## 4. 根因链路

### 4.1 Kimi 能力表缺失，默认走 OpenAI-compatible 全能力路径

当前 capability table 对未知模型使用 permissive default：

```text
supports_tool_choice=True
supports_json_mode=True
supports_json_schema=True
preferred_structured_method='function_calling'
```

`moonshotai/Kimi-K2.6` 没有专门能力声明，因此被当作完整支持
tool calling / structured output 的模型使用。

但 #23 的实际错误表明：

- 普通 `bind_tools(...)` 会触发 `auto tool choice` 后端配置错误；
- `with_structured_output(...)` 经常拿不到可解析对象；
- structured output 返回 `None` 或缺 required fields 很常见。

### 4.2 Analyst 工具调用直接依赖 `bind_tools`

以下 analyst 节点都会用 tool calling：

- Market Analyst: `llm.bind_tools([get_stock_data, get_indicators])`
- News Analyst: `llm.bind_tools([get_news, get_global_news])`
- Fundamentals Analyst: `llm.bind_tools([...financial statement tools...])`

Kimi/Gonka router 后端不稳定支持 tool calling 时，这些节点会在 pipeline 前段
直接失败，导致后续 researcher/trader/PM 完全没有机会执行。

### 4.3 Structured output fallback 没有内容质量校验

Research Manager、Trader、Portfolio Manager 都通过共享 helper 调用结构化输出：

```python
result = structured_llm.invoke(prompt)
return render(result)
```

失败后 fallback 到普通文本：

```python
response = plain_llm.invoke(prompt)
return response.content
```

问题在于：如果 fallback 返回空字符串或残缺字符串，helper 仍然把它当作成功结果。
Portfolio Manager 的空字符串会进入 `final_trade_decision`，graph 也不会抛异常。
runner 只看 `ta.propagate(...)` 是否抛异常，因此把这类结果记成 `ok`。

这解释了为什么有 74 个 ok，但 54 个 final decision 为空。

### 4.4 高并发放大 router + Kimi 的流式不稳定

#23 使用 `max_workers=16`。每个 ticker 不是一次 LLM 调用，而是多个 analyst、
工具调用、研究员辩论、风险辩论、PM 合成等几十次请求。

日志中可见：

- `HTTP/1.1 200 OK`: 2106 次
- `HTTP/1.1 500 Internal Server Error`: 9 次（SDK 自动 retry 后多数恢复）
- `stalled waiting for next chunk`: 104 处文本命中
- attempt-level stalled retry: 79 条

这说明主要瓶颈不是一次性 HTTP 失败，而是长流式 Kimi 输出在 router 路径中途停块。
高并发会增加单个 gateway / backend 的排队、超时和流中断概率。

### 4.5 下游 agent 在空上下文上继续生成，导致“不知所云”

TradingAgents 的数据流是：

```text
Analyst reports -> Research Manager -> Trader -> Risk Analysts -> Portfolio Manager
```

当前段 report 为空或残缺时，下游仍然继续执行。于是 Trader/PM 可能看到：

- 空的 `market_report` / `fundamentals_report`
- 空的 `investment_plan`
- 只有占位符 `Continue`
- 结构化输出 fallback 后的残缺内容

这会触发模型生成类似 `reports were not fully provided in your message` 的文本。
这不是编码乱码，而是上下文链路已经缺失，模型在补洞。

## 6. 当前判断

#23 的问题由四类因素叠加：

1. **模型能力声明错误**：Kimi 走了默认 OpenAI-compatible 全能力路径。
2. **Gonka router 后端能力不足或不一致**：tool calling 报 vLLM auto tool-choice/tool-parser 未启用。
3. **Kimi 长流式生成不稳定**：大量 `winner stalled waiting for next chunk`，重试只能部分救回。
4. **应用层缺少质量门禁**：空 final decision、残缺 report 被当作成功写库。

一句话结论：

> `moonshotai/Kimi-K2.6` 在当前 Gonka router + 16 并发 + TradingAgents
> 多 tool-call / 多 structured-output / 长上下文链路下，不适合作为全链路
> deep+quick 模型直接批跑。#23 的 74 ok 只表示 graph 没抛异常，不表示报告可用。

## 7. 后续排查 / 修复方向

这里先记录方向，不在本文中实现修复。

1. 为 `moonshotai/Kimi-K2.6` 增加 capability override，避免默认发送不兼容的
   `tool_choice` / structured-output function-calling 形态。
2. 对 Gonka/Kimi 路径考虑禁用或改写 tool calling：关键 analyst 可以改成
   pre-fetch 数据后直接 prompt 注入，类似当前 Sentiment Analyst 的模式。
3. Structured output fallback 后必须校验内容：
   - final decision 为空应视为失败；
   - Research Manager / Trader / PM 输出低于阈值或缺 rating/action 应视为失败；
   - 不应把空字符串写成 successful decision。
4. 对 Kimi 降低并发，至少先从 `max_workers=1/2/4` 做 A/B。
5. 优先在 SDK direct mode 下重测 Kimi，区分模型本身问题和 router 问题。
6. dashboard / reports 页面应标识 `ok_empty_final`，避免操作者误读为成功报告。
