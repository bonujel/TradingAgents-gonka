## 问题 0：结构化输出（json_schema）在 Gonka 后端不可用 ✅ 已修复

### 现象

Research Manager / Trader / Portfolio Manager 三个决策节点之前通过 LangChain `with_structured_output(Schema)` 走 OpenAI `response_format={"type":"json_schema", ...}` 路径，让模型直接产出可被 Pydantic 校验的 JSON。生产实测每次调用都进入降级路径，evaluator 拿到的最终 rating 来源不稳定。

### 根因

Gonka 后端的 vLLM 实例对 `response_format=json_schema` 的 completion 部分**硬性限制在 ~3072 token**（vLLM 内部 `EngineArgs.max_logprobs` / guided decoding 的容量约束）。Kimi-K2.6 作为 reasoning model，单次决策包含 reasoning trace + JSON payload，**总长度恒定超过 3072 token**：

- vLLM 在 reasoning 段尾部触发 `finish_reason='length'`
- JSON 段尚未输出 → 返回体的 JSON 部分非法 / 截断
- LangChain `PydanticOutputParser` 抛 `OutputParserException`
- 内置 retry 再跑一次仍然 length truncation → 浪费 ~6000 decode token 后 fallback 到 free-text
- free-text 路径原本有一个简陋的"取第一个 rating 词"启发式，在 Kimi 的辩证型 prose（"虽然 bear 阵营说 Sell，但 bulls 占优；Rating: Buy"）里**经常返回错误评级**

### 修复（已合入 e524168）

- **彻底移除三个决策节点的 structured-output 路径**：RM / Trader / PM 改为 free-text 生成，prompt 模板强制要求开头第一行 `**Rating**: X`（5 档）+ 后续固定结构
- **重写 [tradingagents/agents/utils/rating.py](../tradingagents/agents/utils/rating.py)**：
  - 双 pass 解析：(1) 规范化 label 匹配（`Rating:` / `Recommendation:` / `Action:` / `FINAL TRANSACTION PROPOSAL:` 等 + markdown bold + `:` / `-` / `is` / `=` 多种分隔符）；(2) 通用 rating 词扫描，**从文末倒序匹配**并跳过被否定词（`not` / `avoid` / `rather than` 等）笼罩的命中
  - 5 档词汇 + 词形变化（buying / selling / holding）映射到 canonical 5 档
- 调用图所有路径都用 `parse_rating()` 统一，确保 DB rating / 信号处理器 / memory log 一致

### 验证

跑批观察：parse_rating 在 8192 量级的真实 PM/RM 文本上 **100% 抽到正确评级**；不再有 `OutputParserException`；不再有"PM 输出 Buy 但 DB 写 Sell"这类错位。

## 问题 1：Qwen3-235B-FP8 字节级退化输出 🔵 已定位

### 现象

`Qwen/Qwen3-235B-A22B-Instruct-2507-FP8` 经 Gonka router 调用时，约 **5–7% 的调用**进入字节级退化：

- 输出连续重复某个 token / 词，跑满 `max_tokens` 才停
- 退化形态多样：`/access/access/access...`、`피피피...`、`global global global...`、`체부 업 ...`、`#(c(c(c...`
- HTTP 200 + `finish_reason='length'`，**transport 层无任何异常信号**
- 一个 ticker run 的 ~14 个 LLM 调用里典型出现 1 次以上；首次出现后，被退化 agent 写入 state 的报告污染下游 prompt，**放大失败率**

### 案例

[dev_notes/debug_qwen_degeneration/debug_log_1.json](./debug_qwen_degeneration/debug_log_1.json)
- 节点：News Analyst，step 15
- 模型：`Qwen/Qwen3-235B-A22B-Instruct-2507-FP8`
- `max_tokens=8192`，`finish=length`
- 输出 29,364 字符，前段是 `체부 업 业...` 韩英混合循环，末段是 `global global global...` 持续到 token 用尽

### 根因

Gonka 服务端的 FP8 解码 kernel 对 `max_completion_tokens` 取**特定数值**的请求进入 buggy 解码路径。系统化 sweep 实测：

| `max_completion_tokens` | 退化触发 |
|---:|---|
| 256 | ✅ |
| 2048 | ✅ |
| **4096** | ❌ 实测最稳 |
| 4000 | ✅ |
| 8000 | ✅ |
| 8192（生产历史默认值）| ✅ |

生产 `_GENERATION_DEFAULTS = {"max_tokens": 8192}` **正好命中坏值**。

次要因素：Qwen 在 tool-call args 里偶发把 `curr_date` 写成 `2226-05-23`（多打个 `2`），tool 不校验日期 → 返回不相关新闻 → 退化概率进一步升高。

详细分析：[dev_notes/debug_qwen_degeneration/analysis-2026-05-23.md](./debug_qwen_degeneration/analysis-2026-05-23.md)

### 修复方向（待 commit）

1. **per-family `max_tokens` 配置**：`tradingagents/llm_clients/gonka_client.py` 引入 `_max_tokens_for(model)`，Qwen 默认 **4096**，Kimi 仍 8192（避免触发 Qwen 坏值）；UI Settings 暴露两个独立旋钮
2. **tool 入口 date sanitize**：未来 > 7 天 → clamp 到 today；过去 > 3 年 → clamp 到 3 年前 boundary（防止 hallucinated 日期污染下游）

## 问题 2：Kimi-K2.6 长分析"零可见输出" 🔵 已定位

### 现象

Kimi 作为 deep/quick 模型跑 NVDA + MSFT 单线程（57 分钟、32 次 LLM 调用）后，DB 里两个 ticker 的 `rating=NULL`、`final_decision=""`、`error=NULL` —— **graph 跑完没抛异常，但关键字段是空字符串**。具体 LLM 层面：

- **17 / 32（53%）调用** `finish_reason='length'`（max_tokens 用尽）
- 其中 **7 次**调用 `content_len=0` 同时 finish=length（推理段独占完整 token 预算，可见 content 段从未开始）
- **2 次** `finish_reason=None` + 流式 ~301s 硬切（独立的 timeout 问题）
- 两个 ticker 的 Portfolio Manager **2/2 全部空 content**

### 触发条件（具体）

Kimi 在以下两类 prompt 上**容易完全跑光 token 预算只产 reasoning、不产 content**：

1. **长且歧义的 prompt**——比如 Portfolio Manager 嵌套完整风险辩论历史（aggressive / neutral / conservative × N 轮）+ 多日 past_context lessons 时，prompt 体量到 20k+ 字符，Kimi 的 reasoning trace 会膨胀到吃光预算
2. **辩证型 prompt**——内容自带冲突 / 多视角时（Bull vs Bear、aggressive vs conservative），Kimi 倾向于在 reasoning 阶段反复权衡，**即使 prompt 不长也能耗光**

**反例（修复方向 P1 被证伪）**：把 `max_tokens` 从 8192 提到 **32768**（4×）后重新跑 NVDA + MSFT：
- length 事件从 17 → 16（基本无改善）
- empty-content 事件从 7 → 8（反而 +1）
- 5min stream timeout 从 2 → 4（更大预算 → 流暴露在 timeout 窗口下更久）
- **NVDA + MSFT 的 rating 依然 NULL**

### 案例

[dev_notes/debug_kimi_no_rating_output/debug_log_kimi_reason_no_limit.json](./debug_kimi_no_rating_output/debug_log_kimi_reason_no_limit.json)
- 节点：Portfolio Manager，step 26（MSFT）
- 模型：`moonshotai/Kimi-K2.6`
- `max_tokens=32768`（已提高 4×）
- **prompt 仅 13,068 字符（≈ 3,300 prompt token）**
- `elapsed=211.7s`，`finish=length`，**`content_len=0`**

**这条记录决定性证伪了"prompt 太长导致预算不够"假说**：3.3k token 的 prompt 把 32,768 token 完成预算全部消耗在 reasoning 上。**Kimi 的 reasoning 在 vLLM 上没有硬上限，进一步加大预算只是给它更大的浪费空间。**

### 根因

1. vLLM 把 Kimi 的 CoT 输出在 SSE 流里以 `delta.reasoning_content` 字段发出，**`delta.content` 全部为空**
2. langchain-openai 流式聚合器只读取 `delta.content`，`reasoning_content` 字段被直接丢弃 → `AIMessage.content` 拼接结果为 `""`
3. 当 reasoning 阶段消耗完所有 `max_tokens` 时，vLLM 发 `finish_reason='length'` 关闭流。content 阶段从未开始
4. langchain `generate_from_stream` 看到至少 1 个 generation chunk（最后那个 finish_reason chunk）→ **不抛 "No generations" 异常**
5. RM / Trader / PM 三处节点函数都是赤裸的 `response = llm.invoke(prompt); plan = response.content`，**没有空内容守卫**
6. `""` 进 LangGraph state → graph 提交节点 → runner 看 `final_state.get("final_trade_decision") or ""` 为 `""` → `rating = parse_rating(final_decision) if final_decision else None` → DB 写 `rating=NULL`
7. **runner 全程零异常零警告** → LangGraph 的 node retry policy 不触发（它只在 exception 时启动）

完整链路图：[dev_notes/debug_kimi_no_rating_output/data_flow_trace.md](./debug_kimi_no_rating_output/data_flow_trace.md)
8192 跑根因分析：[dev_notes/debug_kimi_no_rating_output/root_cause_report.md](./debug_kimi_no_rating_output/root_cause_report.md)
32k 重跑对比：[dev_notes/debug_kimi_no_rating_output/rerun_32k_report.md](./debug_kimi_no_rating_output/rerun_32k_report.md)

### 修复方向（确认且待实施）

**P0 — 空内容守卫**：在 RM ([research_manager.py:60](../tradingagents/agents/managers/research_manager.py#L60))、Trader ([trader.py:61](../tradingagents/agents/trader/trader.py#L61))、PM ([portfolio_manager.py:76](../tradingagents/agents/managers/portfolio_manager.py#L76)) 三处统一加：

```python
response = llm.invoke(prompt)
content = response.content if hasattr(response, "content") else str(response)
if not content.strip():
    raise RuntimeError(
        f"<agent_name>: empty content from LLM "
        f"(finish_reason={response.response_metadata.get('finish_reason')!r}); "
        "likely max_tokens exhausted by reasoning."
    )
```

Analyst 节点（Market / News / Fundamentals / Sentiment）也加同等守卫，但要避开 tool_calls 阶段的合法空 content：

```python
if len(result.tool_calls) == 0 and not (result.content or "").strip():
    raise RuntimeError(...)
```

**机制**：抛 `RuntimeError` → LangGraph node retry policy（已存在）触发 → 3 次重试机会。reasoning 长度有随机性（实测两次相邻 prompt 长度差 88 字符即一次成功一次空）→ 重试大概率救回。

**32k 重跑已验证 retry 机制本身工作正常**：MSFT Neutral Analyst step 25 抛 `RemoteProtocolError`（peer closed connection）后 node retry 立即介入并自动救回（content_len 1564）。空内容守卫只是把"static empty"也变成可识别的失败信号。

**P0.5 — `kimi_max_tokens` 回退到 8192**：32k 实测无改善反而恶化。保留 4096–8192 区间足够（Kimi 自然停止时 completion ≈ 2000 token）。

**P1 — 5 分钟流式超时排查**：4 次 `finish=None` 中 3 次精确在 301s ± 1s，强烈疑似 httpx 默认 read timeout。需要给 `gonka_client._STREAMING_DEFAULTS` 加显式 `timeout=1800`。独立于 P0，但属同一类 silent-failure 卫生问题。
