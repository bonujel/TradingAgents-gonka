## 4. 时间聚集性

`peer closed connection` 这 91 个错误**不是平均散布**，而是成簇出现，每簇 2–6
个 ticker 在 1–2 分钟内被一起打挂：

```
17:11 ×6   18:02 ×6   18:19 ×2   19:24 ×1   19:25 ×1
20:14 ×5   20:29 ×2   21:02 ×3   21:20 ×3   21:37 ×2
22:12 ×3   03:18 ×4   04:08 ×4   06:02 ×4   07:02 ×5
08:02 ×5   ...
```

簇状特征说明：**router 上游（new-api → Cloudflare → 执行节点）周期性发生短暂的
TCP/chunked-stream 中断**，连续命中同一时间窗内的多个 ticker。客户端侧的重试
/退避在 runner 中没有实现，故直接计为失败。

## 5. 典型样例

### 5.1 上游断流（最常见）

`CBRE`：

```
RemoteProtocolError: peer closed connection without sending complete
message body (incomplete chunked read)
  File ".../httpx/_transports/default.py", line 101, in map_httpcore_exceptions
  ...
During task with name 'Market Analyst' and id '...'
```

### 5.2 502 Bad Gateway

`LLY`、`KR`、`LMT`、`LYV`、`LOW`、`L`、`LULU`、`LITE`、`MTB`、`LYB`、`MPC`、
`MAR`、`MRSH`、`MLM`、`MAS`、`MA`（16 只，多数集中在同一时段）：

```
openai.InternalServerError: <html>
<head><title>502 Bad Gateway</title></head>
<body><center><h1>502 Bad Gateway</h1></center>
<hr><center>nginx/1.28.3</center></body></html>
```

### 5.3 Gonka 链上 executor 错误

`ABT, AFL, A, AMCR, AIG, AME, AMGN, BALL, BIIB, BG, DELL, EW, EQIX, GIS,
INVH, IRM, JCI, KEYS`（18 只）：

```
openai.APIError: inference: winner inference incomplete
                 (nonce_finished=false)
```

这是 Gonka PoC 2.0 节点的内部状态机错误：选出的 winner 节点声称推理完成，但
共识检查时 nonce 校验失败。属链上层问题，客户端无能为力。

### 5.4 LangGraph 递归超限

`ADSK`、`EBAY`：模型在 Bull/Bear 辩论环节反复要求工具/反驳，达到 100 步硬上限。

```
GraphRecursionError: Recursion limit of 100 reached without hitting a
stop condition.
```

可由 `recursion_limit` 配置抬高，但更可能是 prompt 收敛性问题。

### 5.5 空流（流式断到 0 token）

`ADM` 等 4 只：

```
ValueError: No generations found in stream.
```

通常是 5.1 的"尾部退化"——握手成功但还没拿到任何 chunk 就被关闭。

## 6. 结论与下一步

1. **40.1 % 失败率主要不是模型问题，而是 router/上游网络问题**：68 % 的失败
   是 `peer closed connection`、12 % 是 502 Bad Gateway，加起来 80 % 都指向
   router 上游侧的链接管理 / 反向代理稳定性。
2. **客户端没有重试**：runner 内部一旦 LangGraph 抛异常即落库失败。给单 ticker
   加 **2–3 次指数退避重试**（仅针对 `RemoteProtocolError` / `InternalServerError`
   / `APIConnectionError`）就能把失败率从 40 % 压到个位数。
3. **Gonka 链上 `nonce_finished=false`（18 例）**：客户端层面无法解决，需要 Gonka
   团队跟进 PoC 2.0 executor 状态机。出现频率约 5.4 %，可以容忍。
4. **建议下一轮跑用 SDK 直连路径**：参考 `gonka-sdk-direct-attempt.md`，跳过
   `api.gonkascan.com → new-api` 链路，预计能消掉绝大部分类别 1/2/4/6 的失败。
5. **修 Market Analyst 节点的容错**：所有 73.7 % 的失败都死在第一个 LangGraph
   节点，可以在 `trading_graph.py` 的 invoke 层加一层针对该节点的 retry decorator。
