## 4. 典型样例

### 4.1 No generations found in stream（最常见）

12 只：`EXE`、`FAST`、`FDX`、`BEN`、`HIG` 等。message 简单：

```
[retries=3] ValueError: No generations found in stream.
```

握手成功但流式响应 0 个 token，retry 3 次同样。**已 retry 但不可救**。

### 4.2 数据质量：LLM 输出畸形日期

```
AVGO  → time data '22' does not match format '%Y-%m-%d'
DG    → time data '226-05-15' does not match format '%Y-%m-%d'
FCX   → time data '20 20-04-01' does not match format '%Y-%m-%d'
GD    → time data '206-0-19' does not match format '%Y-%m-%d'
ITW   → time data '20 -005-14' does not match format '%Y-%m-%d'
ZBRA  → time data '226-05-19' does not match format '%Y-%m-%d'
```

LLM 在工具调用参数里把日期截断/插空格了。**属解析层鲁棒性问题**，不属网络/链。

### 4.3 SDK 流式 watchdog 触发

```
ELV  → APIError: inference: winner stalled waiting for next chunk after 1m30s
HCA, PLD, TMUS 同款
```

上游 executor 收到请求开始返回，中间停止发 token 超过 watchdog 阈值（90 s）。
此次 retry=0；**下次会 retry**（白名单已补 `"stalled waiting for next chunk"`）。

### 4.4 Gonka 链 executor bug

```
GIS, KEY, NTRS, PG  → APIError: inference: winner inference incomplete (nonce_finished=false)
```

依旧 4 例，retry 4 次都复现。客户端层面无能为力，需要 Gonka 团队跟进。

## 5. 下一步建议

1. **下次跑预期失败率 ≈ 3 %**：4 个 stalled 加进白名单后会被救回（假设它们真是 transient），失败率 27 → ~23（4.6 %），更乐观下降到 3 %。
2. **数据质量（6 例）**：在调日期解析处加 `try/except` + 失败回退到 `trade_date`，或更早拦截 LLM 输出做格式校验。**这是单点最大可压缩项**——是 100 % 可修复的代码层 bug。
3. **"No generations found in stream"（12 例）**：值得加 instrumentation 看是不是 Qwen3 对某些 prompt 输出过滤，而不是 retry 更多次。
4. **Gonka nonce_finished=false（4 例）**：跟 Gonka 团队反馈失败 ticker 列表，他们查 executor 日志。客户端层面已无优化空间。
