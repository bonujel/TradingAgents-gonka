## 今天的工作

1. **Gonka 双模式 LLM 客户端**:SDK(私钥签名 / 直连节点)与 Router(bearer token / 经 Cloudflare),按 env 自动选路。
2. **应用层 `app/`**:S&P 500 列表 + SQLite + APScheduler + Streamlit 看板,CLI `python -m app.runner [-j N] [TICKERS...]`。
3. **吞吐优化**:开 streaming(`stream=true`)+ ticker 间 ThreadPool 并发(`-j N`)。
4. **vLLM 兼容 fix**:Streaming chunk 偶发把 `\n\n` 攒进 assistant tool_call 消息的 content,vLLM 严格拒空,出栈前改成 `null` 绕过。

## 关键发现

- **Cloudflare 100s 上游超时**:读 Gonka API 节点源码确认——非流式响应在 TA 层是 `io.ReadAll` 全缓冲,流式响应是 `bufio.Scanner` 逐行透传。所以 reasoning 模型(单次推理 >100s)在 router 上只能靠 streaming 救。
- **Kimi K2.6 没上 Gonka 主网**:`api.gonkascan.com` 上选 Kimi 实际路由到 Moonshot 外部后端,SDK 也救不了。**真正落在 Gonka 算力上的目前只有 Qwen3-235B**。
- **vLLM 比 OpenAI 严格**:`content: ""` 或全空白都 400(`messages[i].content: must not be empty`),需要 `null`。Streaming chunk aggregator 偶发触发。

## 没解决 / 未来方向

- **SDK 多 TA fan-out**(最关键):Router 是单点(共享 bandwidthLimiter + 单点 Cloudflare)。换 SDK 路径直连 + 自定义 `endpoint_selection_strategy` 在 K 个 TA 间 round-robin,理论 K× 吞吐。前置:Gonka 主网账户(secp256k1 私钥 + source URL + `publish-pubkey` 上链)。
- **LangGraph 节点内并行**:4 个 analyst 互不依赖,可改并行分支,单 ticker 再降 3-4×。
- **未做**:单测、Dashboard 真人验收、20 只全跑、`-j 8/16` 压测。
