## 一、今天做了什么

围绕"把 TradingAgents 多 agent 投研流水线接到 Gonka 去中心化 LLM 平台、跑 S&P 500
入库 + Streamlit 看板"这条线,完成了从 0 到端到端跑通 4 只票并行的全链路:

1. **Gonka 双模式 LLM 客户端**(`tradingagents/llm_clients/gonka_client.py`)
   - SDK 路径(`gonka-openai` + ECDSA 签名,直连节点)
   - Router 路径(`api.gonkascan.com/v1` + bearer token,经 Cloudflare)
   - 按环境变量自动选路:`GONKA_PRIVATE_KEY` + `GONKA_SOURCE_URL` → SDK;
     `GONKA_API_KEY` → router;两者都缺 → 报错时明确告诉缺哪个。

2. **应用层 `app/` 包**
   - `app/sp500.py`:S&P 500 标的清单(支持 env 覆盖)
   - `app/db.py`:SQLite 持久化(`decisions` + `run_log` 两表,(ticker, trade_date) UPSERT)
   - `app/runner.py`:批量调度 + 单 ticker 跑 + CLI(`python -m app.runner [-j N] [TICKERS...]`)
   - `app/scheduler.py`:APScheduler,默认周一-周五 16:30 America/New_York
   - `app/dashboard.py`:Streamlit 看板,按交易日 + ticker 过滤,展示全部分析报告

3. **吞吐优化(两个关键开关)**
   - **打开 streaming**:`ChatOpenAI(streaming=True, stream_usage=True)`
   - **ticker 间并发**:`ThreadPoolExecutor` 跑批,每个 worker 自己一份
     `TradingAgentsGraph` 实例(避免 `self.curr_state` 跨线程串扰)

4. **vLLM 兼容 fix**:`GonkaStreamSafeChatOpenAI._get_request_payload`
   把 streaming 模式下偶发的"assistant + tool_calls + 空白内容"消息的
   content 字段改成 `None`,绕过 vLLM 的严格校验。

5. **环境**:在 `~/miniconda3/envs/tradingagents`(Python 3.11)装好全部依赖,
   含 `gonka-openai 0.2.6` + `secp256k1` C 扩展原生编译 + langchain 1.x +
   streamlit + apscheduler。

6. **跨仓源码分析**:读了 `gonka/decentralized-api/`(Go 实现)摸清:
   - 请求路径(TA → Executor 两段式转发)
   - 单 TA 的 `bandwidthLimiter`(超限直接 429 + 提示换 TA)
   - 流式 / 非流式响应在 TA 的代理行为(非流式全缓冲,流式逐行透传)
   - 参与者发现接口(`/v1/epochs/current/participants`)
   - **关键事实**:Kimi K2.6 在 Gonka 主网还**没上线**——router 上的 Kimi 实际路由到了 Gonka 网络外的 Moonshot 后端。

## 二、关键发现 / 数据

### 2.1 第一次跑通(non-streaming, Qwen3-235B, 1 analyst minimal config)

- **4m54s**,9 次 LLM 调用 + 1 次 524 重试
- Cloudflare 524 已经出现一次,只是重试救回来了

### 2.2 加 streaming 后(同 minimal 配置)

- **2m53s**(↓41%),7 次调用,**0 次 524**,0 次重试

### 2.3 4 ticker 并行 + 完整默认配置(`-j 4`,4 analyst + 1 轮辩论 + 1 轮风控)

`python -m app.runner -j 4 NVDA AAPL MSFT GOOGL`

| ticker | rating       | per-ticker |
| ------ | ------------ | ---------- |
| NVDA   | Buy          | ~9m        |
| MSFT   | Buy          | ~9.5m      |
| GOOGL  | Hold         | ~10.5m     |
| AAPL   | Underweight  | ~14m       |

**总耗时 836.7s ≈ 13m57s**,4/4 成功,**0 个 524、0 次重试、0 个 failure**。
总时间 ≈ 最长单 ticker 时间 → 4 worker 接近线性 scale。

按 AAPL 这个最长任务的 5× 估算上限,**20 只 S&P 500 大约 30 分钟跑完**,完全在交易日盘后批量窗口内。

## 三、遇到的问题 / 踩的坑

### 3.1 Kimi-K2.6 在 router 上**几乎跑不通**

- Cloudflare 默认 100s 上游响应超时,Kimi 是 reasoning 模型,长 prompt 下单次推理就超。
- 最小配置(1 analyst / 0 辩论 / 3 篇新闻)实测 **call 3 起就 524**,重试也是同样 prompt 同样超。
- 这是结构性冲突,跟 prompt 大小或配置基本无关。
- **跨仓查证**:Gonka 主网当前对外的真实推理模型只有 `Qwen/Qwen3-235B-Instruct`,
  router 上选 Kimi 其实路由到 Gonka **网络外**的 Moonshot 后端——这也解释了 Kimi
  在 router 上比 Qwen 慢一个量级、SDK 路径完全救不了它。

### 3.2 用户给的"SDK 凭据"实际是 router 凭据

- 最初按"只用 SDK 去中心化"路径写了 `GonkaClient`,但用户提供的
  `sk-...` 是 routerscan 签发的 bearer token,**不是** secp256k1 私钥。
- 改成双模式自动调度,router/SDK 共用同一个 `NormalizedChatOpenAI` 壳,
  下游 LangGraph / 结构化输出代码零改动。

### 3.3 第一次开 streaming 立刻翻车

- HTTP 400 `messages[4].content: must not be empty`
- 排查过程:
  - 加 `print` 调试 → 确认 `_get_request_payload` **真的被调用了**(同事
    一开始怀疑 streaming 路径不走这个 hook,实测打脸)
  - 打出 message[4] 的 `repr` → `content='\n\n\n\n\n\n\n'`,7 个换行
- 根因:LangChain streaming chunk aggregator 偶尔把若干 `\n` chunk 攒进
  `content`,生成"只有 tool_calls + 空白文本"的 AIMessage。OpenAI API
  容忍这个,vLLM 严格拒绝。
- 修复:重写 hook 检查 `content.strip() == ""`,改成 `None`。

### 3.4 监控 / 调试开销

- TradingAgents `debug=False` 模式不打任何中间日志,3 分钟看不到进度
  以为卡死。
- 已经给 `app/runner.py` 加了"进入 propagate / 退出 propagate"的 INFO 日志,
  以及 `[%(threadName)s]` 用于看多 worker 的工作分布。

## 四、还没解决 / 未来可能的方案

### 4.1 真正"用满 Gonka 算力"需要 SDK 路径 + 多 TA fan-out

- Router 是单点,所有请求都经过同一个 Gonka API 节点 + 共用一个 bandwidth limiter
- SDK 路径直连 TA + 可自定义 `endpoint_selection_strategy`,K 个 TA 大致 K× 吞吐
- 前置条件:申请到 Gonka 主网 `inferenced` 账户(secp256k1 私钥)+ 公开节点
  source URL,做 `inferenced publish-pubkey` 上链
- 同时也直接绕开 Cloudflare 这一跳,延迟更稳

### 4.2 Kimi K2.6 等真上线 Gonka 再测

- 现在 router 上的 Kimi 是套娃到 Moonshot 外部,意义不大
- 一旦 Gonka 主网部署 Kimi 节点,通过 SDK 路径(不过 Cloudflare 100s)有望直接用上
- 准备工作:`gonka_client.py` 已经支持任意 model 名,切换只改环境变量一行

### 4.3 LangGraph 节点级并行(单 ticker 内 4 analyst 同时跑)

- 现在 4 个 analyst(market / sentiment / news / fundamentals)串行
- 互相之间无数据依赖,可改成 LangGraph 并行分支 + reducer 汇合
- 单 ticker 提速 3-4×,叠加 ticker 间并发后再降一倍 walltime
- 改动量较大,涉及 `trading_graph.py` + `agent_states.py` 的 reducer 定义,
  排在 4.1 之后做

### 4.4 单测覆盖 + CI

- `GonkaStreamSafeChatOpenAI._get_request_payload` 这种边界 fix 应该
  有单测固定下来(直接构造 messages 列表跑 hook,断言出栈内容)
- LangChain / vLLM / Gonka 三方都会发版,任何一边的行为变化都可能让 fix 失效
- 还没写,明天可以补

### 4.5 Dashboard 还没真人验收

- 起得来、health check 200、能展示 4 行 Run B 的数据,但 UI 体验本人没看
- 明天演示前可以本地 `streamlit run app/dashboard.py` 过一遍

### 4.6 批量 20 只全跑还没真做

- 按 Run B 数据估算 ~30 分钟
- 如果今天演示能演 4 只票 14 分钟的 Run B 数据 + 20 只票的预估,效果差不多
